# 指标口径手册

> 本手册的所有数字均由 `src/metrics.py` 与 `sql/02_kpi_analysis.sql` 双实现计算并逐格对账（17 项，容差 1e-6）。
> 统计主体统一为 **account（企业账户）**，本数据集不存在 user 级表，因此「人均」类指标实际为「户均」。

## 统计主体与粒度

全项目的分析主体是企业账户，不是自然人用户。数据中不存在 user 明细表，所以任何以「人」为单位的指标都不可计算，包括人均使用时长、日活用户数、单用户贡献收入。凡涉及此类口径，一律改用账户口径并如实命名，例如「户均使用功能数」而不是「人均使用功能数」。指标字典中每项都标注了可计算、部分可计算或不可计算及其原因，不允许用近似值填充。

## 激活率的定义与替代口径

标准定义是「注册后 N 日内完成首次有效任务」的账户占比。本数据集**无法计算**该指标，因为使用记录与注册时间不连贯：500 个账户中有 490 个的首次使用日早于注册日，中位提前 400 天。若强行按注册日计算，激活率会是 7/500 即 1.4%，这个数字反映的是数据缺陷而不是业务表现。因此真实数据侧改用「以首次使用日为锚」的替代口径，指标名称中不带「注册」二字；「注册→首次请求」这条链路改用模拟日志单独分析。

## 留存的两种口径

第一种是月度同期群留存：以账户首次使用月为队列，统计后续每月仍产生使用记录的账户占该队列规模的比例。第二种是以活跃窗口定义的留存：某账户在观察窗口内是否仍有订阅与使用。本数据集因左截断严重（88% 的账户首次使用落在 2023 年 1 月），同期群只剩一个巨大队列，第一年之后的留存曲线没有区分度，因此真实数据只报告窗口留存，同期群留存仅在模拟数据上做演示。

## 流失的三套口径

数据中同时存在三个「流失」定义，三者互不相等。流失事件表有 600 行、覆盖 352 个账户，其中 61 行是流失后复活；账户表的 `churn_flag` 标记只有 110 个为真；两处同时命中的仅 75 个。主口径取「流失事件表去重账户数」，因为事件表带日期与原因、可做时间序列，快照标签无法追溯。复活记录单独列出、不重复计入。`churn_flag` 降级为交叉校验字段，差异在报告中披露。

## 收入与 MRR 的取数规则

MRR 取账户在观察期末月的有效订阅金额。由于订阅存在一对多且严重重叠——5,257 个「账户-月」组合中有 4,695 组（89.3%）有多条同时生效的订阅——直接求和会重复计入。胜出规则为：`start_date` 最新者优先，其次 `mrr` 最高者，最后以 `subscription_id` 字典序兜底。该规则在 `v_account_month` 视图中实现，Python 侧有独立实现并与之逐格对账。
