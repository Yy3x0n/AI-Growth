# AI 使用与成本核算口径

> 本文的口径适用于模拟 AI 请求日志（69,403 行）。成本为按公开单价快照的**估算值**，
> 不是真实账单；报告中不得写成「服务成本」。

## 三个核心指标的定义

请求量按请求 ID 计数，同一请求不重复计入。成功率等于状态为 success 的请求数除以总请求数，它度量的是技术成功率，不涉及回答质量。有效任务的定义是「请求成功，且输出 token 数不低于 50」，取 50 是为了排除技术成功但业务无价值的空返回。P95 延迟采用最近秩法，即排序后取第 ceil(0.95n) 个值，不使用线性插值。

## 为什么 P95 必须用最近秩法

MySQL 没有 `PERCENTILE_CONT` 函数，SQL 侧只能用窗口函数按排名取第 ceil(0.95n) 行。如果 Python 侧使用默认的线性插值，两边会长期相差 1 到 200 毫秒，而且差值没有规律——这类「对不上但不报错」的问题最难排查。因此 SQL 视图与 Pandas 实现统一采用最近秩法，并在对账脚本中逐列比对。该口径已通过 23 个指标列的逐格对账验证。

## 成本计算与假设

成本按行计算后求和，不采用「总 token 乘单价」的近似算法。输入与输出分别计价：未命中缓存的输入单价为每百万 token 0.15 美元，输出单价为每百万 token 0.60 美元，快照日期为 2026 年 9 月 18 日。缓存命中率按 0 计算，即全部按未命中计价，这是保守的上界估算。峰谷计费未细分。列名固定为 `estimated_cost_usd_at_assumed_price`，禁止简写为 cost，以免被误读为真实成本。

## 成本结构与请求结构不匹配

三个 AI 功能中，文档总结占 30.0% 的请求却消耗 53.0% 的成本，单次成本是 AI 问答的 3.7 倍，每千次请求成本 0.843 美元对 0.229 美元。根因在输入侧：文档总结的中位输入 token 为 3,800，问答只有 620，相差约六倍；AI 写作的输出 token 最高但输入较低。因此成本优化的杠杆在文档总结，而不在调用量最大的问答。按请求数做容量规划会低估成本约一半。

## 使用集中度

请求量高度集中：前 10% 的账户（40 个）贡献 57.2% 的请求，前 20%（79 个）贡献 76.4%，前 50%（198 个）贡献 93.9%。这个分布对限额策略有直接影响：按账户设配额主要影响那 40 个重度客户，需商务介入；按请求总量限流会在高峰时先伤到他们，属稳定性问题。两者不能混为一谈。

## 不能从这个口径推出的结论

第一，成功率 89.98% 只是技术成功率，日志中没有人工评分、没有正确性标注，因此不能推断回答质量。第二，成本是估算值，只能用于相对比较。第三，AI 使用量与收入或留存的相关关系由模拟生成逻辑决定，不是业务发现，本项目主动不做这类归因。
