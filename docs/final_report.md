# AI 应用增长与数据运营：从指标到 RAG 诊断助手

> 一个端到端的 B2B AI SaaS 增长分析项目：数据入仓 → 指标体系 → 客户分层 → A/B 实验 →
> AI 成本分析 → RAG 知识库 → 带数字审计的诊断报告。
>
> 编制日期：2026-11-02　·　代码仓库：https://github.com/Yy3x0n/AI-Growth

---

## 0. 先说数据边界

本项目使用三类性质完全不同的数据，**任何结论都必须带对应标注**：

| 标注 | 数据 | 性质 | 允许的表述 |
|---|---|---|---|
| **T1** | RavenStack 五张 CSV | 公开**合成** SaaS 数据 | 「公开合成数据集」 |
| **T2** | `data/simulated/ai_request_logs.csv` | 固定种子与显式规则**生成** | 「模拟日志」 |
| **T3** | `data/simulated/ab_test_simulated.csv` | 固定种子的**模拟**实验 | 「模拟实验」 |

**本仓库不代表任何真实企业的业绩。** AI 成本为「假设单价」估算值，A/B 的 p 值不构成真实业务证据。

## 1. 这个项目要回答的问题

给定一家 B2B AI SaaS 公司的订阅、使用、工单与流失数据，回答四个运营问题：

1. 收入到底集中在谁身上，谁值得投入人力？
2. 新客为什么没被激活、AI 功能为什么用不起来？
3. 一次新手引导改版到底该不该上线？
4. AI 功能的成本花在哪，能不能降？

最后一个问题是差异化所在：不是"再做一个 BI 看板"，而是**让大模型基于事实写诊断报告，
并且能证明它没有编数字**。

## 2. 架构与数据流

```
T1 五张 CSV ──► MySQL(暂存表→强类型) ──► KPI 视图层 ──► SQL/Pandas 双实现对账
                                              │
                                              ├──► 客户分层(六层) ──► 策略手册
                                              │
T2 模拟日志 ──► AI 使用分析(成本/延迟/异常检测)
T3 模拟实验 ──► A/B 检验 + 检验框架自校验
                                              │
12 份知识文档 ──► 切块 ──► BGE 向量化 ──► ChromaDB
                                              │
用户提问 ──► 场景选择 ──► 白名单函数取数 ──► 检索 ──► LLM 成文 ──► 数字审计 ──► 报告
```

**关键约束：模型全程拿不到数据库连接。** 它只能选场景，参数由白名单函数校验后换算成固定计算。
即使提示词被注入，最大后果也只是"用合法参数多查一次"。

## 3. 六个模块做了什么、得出什么

### 3.1 数据质量审查（24 项检查）

33,100 行 / 5 表 / 24 个月。主键、外键、日期倒挂全部干净，但有五个问题改变了分析口径：

| 发现 | 数值 | 后果 |
|---|---|---|
| 首次使用早于注册日 | **490 / 500** 账户（中位早 400 天） | 「注册→首次使用」漏斗无法构造 |
| 使用记录早于所挂订阅开始 | 19,142 / 25,000（76.6%） | 使用与订阅时间轴不连贯 |
| 落在该账户任一订阅区间内 | 仅 **22.5%** | 同上 |
| `feature_name` 为编号 | `feature_1..40`，无 AI 语义 | 不能称"AI 问答" |
| 流失三套口径互不相等 | 600 事件 / 352 账户 / 110 标记 | 「流失率」可算出 67.8% 与 22% |
| 订阅一对多且重叠 | 4,695 / 5,257 组（89.3%） | 直接 `SUM(mrr)` 会重复计入 |

**最重要的一条**：这份数据**没有生命周期**。每月活跃账户 24 个月稳定在 410~440，
每个账户起步就已使用 9~40 个功能，88% 的"首次使用"都落在数据起始月。
因此**注册→激活→留存→实验这条链，在 T1 上任何一环都不成立**。
诚实处置是：真实数据只做截面与结构，生命周期与实验交给模拟数据。详见
[`data_capability_assessment.md`](data_capability_assessment.md)。

### 3.2 指标体系与客户分层

**双实现对账**：`src/metrics.py`（Pandas）与 SQL 视图独立复算，**17 项指标逐格比对全部一致**
（容差 1e-6），不是抽样。

六层互斥分层，阈值全部来自实际分布并落库为 `segment_threshold` 单表（避免 SQL 与 Python 漂移）：

| 层 | 账户 | 收入占比 | 特征 |
|---|---:|---:|---|
| 零 MRR | 69 | 0% | 订阅仍有效但金额为 0（**不是流失**） |
| 风险关注 | 93 | 22.9% | 高错误率 / 低 CSAT / 升级工单 |
| **高价值** | **102** | **57.1%** | MRR ≥ P75 |
| 深度采用 | 63 | 5.5% | 功能数 ≥ P75，但收入反而低 |
| 浅层采用 | 58 | 5.0% | 功能数 ≤ P25，工单最多（4.74 次） |
| 稳健基础 | 115 | 9.4% | — |

三个有行动价值的结论：

1. **20.4% 的账户贡献 57.1% 的收入**；与风险层合计不到四成账户撑起八成收入。
2. **功能用得多 ≠ 付得多**：深度采用层均 MRR 1,125，高价值层 7,204。功能渗透率不能当收入潜力的代理。
3. **浅层采用层工单最多（4.74 次）**：不会用的人更依赖人工支持，功能采用同时是服务成本控制动作。

### 3.3 A/B 实验

数据集只有 500 个账户，每臂 250 时只能检测约 **46%** 的相对提升，运营上不可能。
因此按设计样本量（每臂 2,193）生成模拟实验，并在三处文档披露这一偏离。

| 指标 | 对照 | 实验 | 结论 |
|---|---:|---:|---|
| 7 日首次有效任务率 | 25.17% | 26.86% | +1.69pp，**p=0.203 不显著** |
| 7 日后错误率 | 10.58% | 10.93% | **显著恶化**，p=0.019 |
| 7 日内工单率 | 9.85% | 13.22% | **显著恶化**，p=0.0005 |

**决策：证据不足，不建议上线。** 没有为了"跑出显著"换种子。

为了让这个 p 值可信，用 2,000 次 Monte Carlo 校验检验框架本身：

| 检验 | 名义值 | 实测 | 判定 |
|---|---:|---:|---|
| 第一类错误率 | 5% | **4.65%** | 通过 |
| 功效 | 80% | **80.15%** | 通过 |
| 95% CI 覆盖率 | 95% | **94.80%** | 通过 |
| SRM 误报率 | 0.1% | 0.2% | 通过 |
| SRM 检出率（52/48） | — | **27.2%** | 已量化：只能兜严重失衡 |

### 3.4 AI 使用与成本

69,403 次请求 / 397 账户 / 成功率 89.98% / 估算成本 $33.16（假设单价）。

**核心结论：请求结构与成本结构错位。**

| 功能 | 请求占比 | 成本占比 | 单次成本 |
|---|---:|---:|---:|
| AI 问答 | 50.3% | 24.1% | $0.00023 |
| **文档总结** | **30.0%** | **53.0%** | **$0.00084** |
| AI 写作 | 19.7% | 22.9% | $0.00060 |

文档总结占三成请求却吃掉过半成本，单次是问答的 3.7 倍，根因在输入 token（中位 3,800 vs 620）。
**成本杠杆在文档总结，不在调用量最大的问答**；按请求数做容量规划会低估成本约一半。

另有一条通用规则做异常检测（低于该功能基线 3 个二项标准误），自动命中 13 个「功能-日」，
全部落在预设故障窗口内且全属问答——规则事先不知道窗口位置，说明它能迁移到真实日志。

### 3.5 RAG 知识库

12 份文档（6 份承载实测数据 + 6 份模拟产品流程），67 个块，BGE-small-zh 512 维。

| 指标 | 值 |
|---|---:|
| Hit@3 | 1.0000 |
| Top1 准确率 | 0.8667 |
| Recall@3 | 1.0000 |
| MRR | 0.9333 |

**这个数字要打折看**：18 题评估集由我自己出题、自己写文档，属于自出题自答；
Hit@3 满分掩盖了两题第一名错误。真实用户的问法（口语、指代、上下文）完全没覆盖。

过程中修掉一个真实缺陷：跨文档题的 Top-3 被同一份文档挤满，加「每文档最多 2 条」后
跨文档 Recall@3 从 0.8333 升到 1.0。**这是看结果后做的改动，评估集对该改动已非留出集**，
因此在文档里标注为形成性评估。

### 3.6 运营诊断助手（RAG + LLM）

三个白名单场景，参数四重校验（格式 / 观察期 / 区间顺序 / 跨度），拒绝未知场景与多余参数。
固定 8 段输出：问题概述、数据事实、知识依据、原因假设、目标客群、运营动作、主次指标、数据限制。

**核心是数字审计**：把指标 JSON 里所有数字抽成白名单，正文每个数字都必须能追溯。

实测拦截效果：

| 模型输出 | 判定 |
|---|---|
| `上季度激活率仅23.4%` | **拦下**（编造） |
| `预计可提升18.7个百分点` | **拦下**（编造） |
| `激活率约43.1%`（真值 43.06%） | **拦下**（失真） |
| `从9.176%下降到8.555%` | 通过（`0.09176` 的合法换算） |

三份报告实测：19.7s / 18.6s / 25.6s，其中一份触发重试后通过。

**必须披露的盲区**：审计只能查"数字是否来自数据"，查不了"数字有没有用错地方"。
真实发生过：模型把某账户的 `inactive_days: 53` 写成"前 10% 账户贡献了 53% 的请求"，审计放行。
所以这套护栏的定位是**让人工复核有的放矢，不是替代人工复核**。

## 4. 方法论上真正下功夫的三件事

### 4.1 双实现互相对账

任何关键指标都用 SQL 与 Pandas 各算一遍，逐格比对。17 项指标、24 行月度、500 行画像全比，
不是抽样。这能抓住 join 写错、去重规则不一致这类"不报错但结论偏"的问题。

### 4.2 模拟数据锚定真实时间轴

模拟 AI 日志不是随机撒点：先用**真实订阅**展开「账户-月」网格（覆盖当月 15 日才算活跃），
再用**真实流失事件**截断。这里踩过一个坑——4,514/5,000 条订阅 `end_date` 为空，
我最初填成观察期末，结果活跃账户曲线只涨不跌，等于把流失抹掉了。修正后 2 → 212 → 195。

每次生成都做参数恢复自检：从数据反推设定参数比对，六项偏差全部 <0.3pp。
这能抓住"生成器写错但没人发现"——数据看起来照样像真的。

### 4.3 让"我错了"可被发现

- 阈值敏感性检查：功能数 P25=24、P75=32 只差 8 个取值点，阈值 ±20% 时深度采用层在 5~167 户间跳变，
  因此这两层只能描述性使用。已做成 `--sensitivity` 可复现。
- 阶段 6 复核时发现分层第一层命名错误：叫「已停付」，但那 69 户**全部持有有效订阅**，
  只是金额为 0。已改名为「零 MRR」，并修正了由此推出的运营动作（从"唤回"改为"先核实计费"）。
  **命名错误比算错数更危险**，因为它会让人在错误假设上做决策。

## 6. 如实披露：改写了什么、没做什么

**改写（都有理由，且记录在案）**

| 编号 | 原设计 | 改为 | 理由 |
|---|---|---|---|
| C-10 | 注册→首次使用漏斗 | 首次使用为锚 + T1 只做截面 | 时间轴不连贯，原漏斗不可构造 |
| C-13 | 账户 ID 必须真实 | T3 用合成 ID | 500 账户撑不起实验功效，复用 ID 破坏独立性 |
| C-14 | DeepSeek | GLM-4-Flash | 免费额度，可反复重跑验证审计 |

**没做的**

- 没有预测模型 / 流失打分：500 账户、无生命周期，做出来只会过拟合。
- 没做用户级指标（DAU、人均时长）：数据里没有 user 表。
- 没接真实触达、没改产品配置：本项目的产出是建议，不是执行。

## 7. 如何复现

```bash
# 0) 环境
git clone git@github.com:Yy3x0n/AI-Growth.git && cd AI-Growth
git config core.hooksPath .githooks      # 密钥拦截钩子（公开仓库必做）
cp .env.example .env                      # 填 GLM_API_KEY 与 MySQL 密码

# 1) 一键跑完全链路（幂等）
bash scripts/reproduce.sh

# 2) 或分步执行
python scripts/download_data.py
python scripts/profile_data.py
python scripts/load_to_mysql.py
python scripts/run_sql.py sql/02_kpi_analysis.sql
python scripts/run_analysis.py            # 指标 + SQL/Pandas 对账
python scripts/simulate_data.py           # T2/T3 模拟数据 + 参数恢复自检
python scripts/run_ai_analysis.py
python scripts/run_ab_test.py
python scripts/build_knowledge_base.py    # 建索引（幂等）
python scripts/evaluate_retrieval.py
python scripts/ask_ops_assistant.py --scenario activation_diagnosis \
    --start-date 2024-07-01 --end-date 2024-09-30
python scripts/build_dashboard.py         # 6 张 PNG 图 + 静态图版看板
python scripts/build_bi_dataset.py && python scripts/build_html_dashboard.py
                                          # BI 数据层 + 交互版看板（ECharts 单文件）
pytest -q
```

## 9. 如果继续做，下一步会是什么

1. **把审计从"数值存在性"推进到"语义归属"**：现在 `inactive_days: 53` 被当成"53% 请求占比"
   也能通过。可行方向是让模型输出结构化引用（`{"value": 53, "field": "inactive_days"}`），
   由代码校验字段是否存在、量纲是否匹配。
2. **给 RAG 建真正的留出集**：现在的 18 题参与过调优。应另建一批不看结果的题目复核。
3. **A/B 换成序列检验**：固定样本量的前提是能等，实际业务更常见的是"边跑边看"，
   需要 alpha spending 控制多重比较。
