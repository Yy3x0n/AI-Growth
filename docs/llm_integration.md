# LLM 集成说明（模块 F 后半段）

> 状态：阶段 5 完成。模型已从任务书默认的 DeepSeek 切到**智谱 GLM-4-Flash（免费）**。
> 本文记录选型依据、链路结构、护栏机制的实际效果，以及**这套护栏做不到什么**。

---

## 1. 为什么换成 GLM-4-Flash

任务书 §4.5 指定 DeepSeek。实际执行时改用智谱 GLM，原因只有一条：**免费额度足以跑完全流程**，
而项目需要反复重跑报告来验证审计逻辑，按次计费会在调参阶段迅速烧掉预算。

选型不是拍脑袋，是同一把 Key 下逐个实测出来的（2026-11-02，单轮对话，`max_tokens=800`）：

| 模型 | 首字延迟 | 是否带思维链 | 中文质量 | 结论 |
|---|---:|---|---|---|
| `glm-4-flash` | **1.9s** | 否 | 可用 | **采用** |
| `glm-4.5-flash` | 18.8s | 是（192 reasoning tokens） | 更好 | 太慢，单份报告要等 1 分钟 |
| `glm-5.3-flash` | 6.8s | 是（240 reasoning tokens） | 更好 | 备选 |
| `glm-4.7` | 5.9s+ | 是 | — | 未采用 |

一个容易踩的坑：**思维链模型的 `max_tokens` 会被思考过程吃掉**。
用 `max_tokens=16` 测 `glm-4.5-flash` 时返回 200 但 `content` 为空，
一度以为模型不可用——实际是 16 个 token 全用在 reasoning 上了。
判断"模型是否可用"不能只看 HTTP 状态码。

切换方式：改 `.env` 里的 `LLM_MODEL`，代码不用动。三家都是 OpenAI 兼容的
`/chat/completions`，差异只在 `base_url` 与模型名。

## 2. 链路结构

```
用户问题 / 场景名
      │
      ├─► ① ops_metrics.run_scenario()      ← 白名单函数，参数校验在这里
      │       └─ 输出：指标 JSON + 口径定义 + 数据限制
      │
      ├─► ② retriever.retrieve()            ← 向量检索（阶段 4 的索引）
      │       └─ 输出：Top-K 片段（含文档名、章节、距离）
      │
      ├─► ③ LLMClient.chat(json_mode)       ← GLM-4-Flash
      │       └─ 输出：8 段结构化 JSON
      │
      ├─► ④ audit.audit_report()            ← 数字审计 + 引用校验
      │       ├─ 通过 → 落盘
      │       └─ 不通过 → 带具体违规项重试一次
      │                  └─ 仍不通过 → 降级为确定性模板
      │
      └─► ⑤ render_markdown()               ← 固定 8 段渲染
```

**模型全程拿不到数据库连接。** 它只能"选场景"，参数由 `ops_metrics` 校验后
换算成固定的 Pandas 计算。即使提示词被注入，最大后果也只是"用合法参数多查一次"。

## 3. 三个白名单函数

| 场景 | 函数 | 数据源 | 说明 |
|---|---|---|---|
| `activation_diagnosis` | `get_activation_metrics` | 真实（T1） | 注册 → 首次付费订阅转化 |
| `feature_adoption_diagnosis` | `get_feature_adoption_metrics` | 模拟（T2）默认，可选真实 | AI 三功能采用率及环比 |
| `low_activity_customer` | `get_low_activity_accounts` | 真实（T1） | 沉睡账户清单与收入风险 |

### 3.1 激活口径被改写了，理由必须说清

任务书原本要求「注册 → 首次请求 → 首次有效任务」漏斗。**这条链在这份数据上不成立**：
490/500 个账户的首次使用时间早于注册日，中位早 400 天（阶段 1 的 Q-23）。
硬算会得到一个 1.4% 的"激活率"，那是数据缺陷的产物，不是业务结论。

因此改用「注册 → 首次付费订阅」。这是 SaaS 语境下同样成立的激活定义，且这套数据真实支持。
报告正文和 `caveats` 里都写明了这次改写，不允许悄悄替换。

### 3.2 右删失：一个不会报错但会让结论偏移的坑

2024-12-25 注册的账户，到数据截止日只有 6 天，用 30 天窗口衡量它"没转化"是错的。
所以分母只算「注册日 + 窗口 <= 2024-12-31」的账户：

```python
cohort["is_observed"] = cohort["signup_date"] + pd.Timedelta(days=window_days) <= obs_end
```

代价是 `cohort_size != eligible_size`，这看起来像 bug，其实是正确行为，
所以在 `caveats` 里显式解释了这一差异。

## 4. 数字审计：本模块的核心

### 4.1 为什么需要

让 LLM 写运营报告，最大的风险不是文笔差，而是**它会把数字编得很像真的**。
"激活率提升 1.69 个百分点"（对）与"提升了 6.7%"（把绝对差当相对差）、
"上季度 23.4%"（凭空捏造），这三句在中文里读起来毫无违和感。

所以不依赖模型自觉，而是事后核验：
把指标 JSON 里出现过的所有数字抽成白名单，正文里每个数字都必须能在其中找到来源。

### 4.2 实现要点

| 问题 | 做法 | 为什么 |
|---|---|---|
| `0.4306` 写成 `43.06%` 算不算编造 | 不算。0~1 的小数自动派生出 ×100 形态 | 否则所有百分比写法都会被误杀 |
| 小数位数不同怎么办 | **数值容差**匹配（相对 5e-4），不做字符串比对 | 实测字符串精确比对直接导致 3 处误报 |
| `43.06` 写成 `43.1` | 判违规 | 容差是为了容纳位数换算，不是允许四舍五入失真 |
| 「截至2024年12月31日」 | 日期分量（2024/12/31）一并放行 | 中文写法会把日期拆成三个数字 |
| `174,342` 与 `174342` | 视为同一个数 | 千分位不应被当成不同数字 |

### 4.3 实测效果

首轮实现用字符串精确比对，跑真实模型时出现 3 处误报（`9.176%`、`8.555%`、`0.621`）。
改成容差匹配后，同时验证了**不误报也不漏报**：

| 输入 | 判定 | 是否正确 |
|---|---|---|
| `激活率为43.06%，高于上期的30.77%` | 通过 | ✓ |
| `从上一季度的9.176%下降到8.555%`（指标存 0.09176 / 0.08555） | 通过 | ✓ |
| `截至2024年12月31日，共有72个账户` | 通过 | ✓ |
| `上季度激活率仅23.4%` | **拦下** | ✓ 编造 |
| `预计可提升18.7个百分点` | **拦下** | ✓ 编造 |
| `激活率约43.1%` | **拦下** | ✓ 四舍五入失真 |
| `MRR 为1,286,108元` | **拦下** | ✓ 编造 |

审计拦截不是终点，还要让重试**可操作**：违规项会附上"最接近的合法值"。
实测发现小模型最常见的错误不是凭空编，而是**漏一个数量级**——把 `0.8555` 写成 `8.555%`。
只告诉它"这个数字不合法"它改不对，告诉它"最接近的是 85.55"才能一次改对。

### 4.4 这套护栏做不到什么（必须明说）

**它只能查"数字是否来自数据"，不能查"数字有没有用错地方"。**

这不是理论风险，实测真的发生过一次。`low_activity_customer` 场景的一份报告里，模型写道：

> 依据：知识片段3中提到前 10% 的账户贡献了 **53%** 的请求

`53` 确实存在于指标 JSON 中——但它是某个沉睡账户的 `inactive_days: 53`，
与"请求占比"毫无关系。**审计放行了，因为它只做数值存在性检查。**

其它已知盲区：

- 中文数词（"三成"、"两倍"、"翻倍"）不在抽取范围，会漏检。
- 指标名是否存在不检查。模型建议"护栏指标：引导流程完成率"时，我们并没有这个指标，但它不含数字，审计管不到。
- 因果误读（把相关说成因果）完全靠提示词约束 + 人工复核，机械护栏无法处理。

**结论：审计把"编数字"从高频风险降到低频，但没有消除"读起来对、其实错"的风险。
这套东西的定位是"让人工复核有的放矢"，不是"替代人工复核"。**

## 5. 引用校验

每条知识引用必须满足：文档名在本次检索结果中，且章节名能对上（字符级 Jaccard ≥ 0.6）。

这一步防的是"模型凭训练记忆编一个文档名"。它完全可能写出
`13_growth_hacking_playbook.md` 这种看起来毫无破绽的文件名，但只要本次没检索到，一律判违规。

章节名采用宽松匹配（去标点后包含或 Jaccard ≥ 0.6），因为模型常把
「P95 延迟口径」写成「P95 延迟」。但文档名要求严格一致——文档名是可枚举的，章节名不是。

## 6. 降级设计

| 情况 | 处理 | 理由 |
|---|---|---|
| 模型调用失败（网络 / 401 / 超时） | **立即**降级，不重试 | 重试不会让密钥变对，只会让用户多等 |
| 输出不是合法 JSON | 重试一次，明确要求"只输出 JSON" | 小模型常带 markdown 围栏，值得再给一次机会 |
| 数字审计不过 | 重试一次，附带具体违规项 | 这是最可能被修好的失败模式 |
| 两次都不过 | 降级为确定性模板 | 宁可给"只有事实没有润色"的报告，也不给"读起来很顺但数字靠编"的报告 |

降级不是空白页：仍保留指标事实与检索到的文档名，只去掉原因假设与运营建议
（因为这两段最依赖推断，在缺少审计时最不可信）。降级事实会写进报告头部与 Markdown 横幅。

CLI 退出码也做了区分：`0` 正常，`1` 降级，`2` 参数或配置错误。
这样自动化流程能发现"这次结果不可直接采用"。

## 7. 实测结果

三份报告，真实调用 GLM-4-Flash：

| 场景 | 延迟 | Token（入+出） | 尝试次数 | 数字核验 | 引用 | 状态 |
|---|---:|---|---:|---:|---:|---|
| 新客激活 | 19.7s | 2039 + 447 | 1 | 6 处 | 2 条 | 正常 |
| AI 功能采用 | 18.6s | 1973 + 424 | 1 | 9 处 | 1 条 | 正常 |
| 低活跃客户 | 25.6s | 3057 + 732 | **2** | 12 处 | 3 条 | 正常（重试后通过） |

三点观察：

1. **延迟 19~26 秒**，主要成本在输入侧（约 2000~3000 token 的指标 JSON + 知识片段）。
   这对"点一下等半分钟"的运营工具是可接受的，对实时问答不行。
2. **低活跃场景触发了一次重试**，说明审计不是摆设。重试后代价是 +1000 输入 token。
3. **激活场景的检索距离 0.4035 超过了 0.40 阈值**，报告头部自动挂了警告：
   "知识库对该问题的覆盖可能不足，引用仅作参考"。
   这条提示很有必要——那两份被引用的文档（03 激活漏斗、06 数据边界）讲的其实是
   "这个指标不可计算"，而不是"激活率为什么变化"，属于**相关但不对口**。

## 8. 关于模型选型的取舍

`glm-4-flash` 是个小模型，实测中的具体弱点：

- JSON 模式偶尔返回英文结论（提示词里已加"必须用简体中文"后仍出现过一次）。
- 会把"知识片段 N"当依据，而不写文档名，导致依据不可核验。
- 会自己算差值（8.555 − 9.176 = 0.621），即使提示词明令禁止。

换成带思维链的 `glm-5.3-flash` 应该能改善这些，代价是延迟翻倍。
**本项目保留 `glm-4-flash` 的理由是：这些缺陷恰好是审计层能兜住的**
（英文结论不影响数字审计；自算差值会被判违规并触发重试）。
如果审计层没做，就必须换更强的模型——这反过来说明，**护栏的价值在于让你能用便宜模型**。

## 9. 如何运行

```bash
# 默认用 .env 里的 LLM_PROVIDER=glm / GLM_MODEL=glm-4-flash
python scripts/ask_ops_assistant.py --scenario activation_diagnosis \
    --start-date 2024-07-01 --end-date 2024-09-30

python scripts/ask_ops_assistant.py --scenario feature_adoption_diagnosis \
    --start-date 2024-10-01 --end-date 2024-12-31

python scripts/ask_ops_assistant.py --scenario low_activity_customer --as-of 2024-12-31

# 不联网验证链路
python scripts/ask_ops_assistant.py --scenario low_activity_customer \
    --as-of 2024-12-31 --mock
```

产物落在 `outputs/reports/`：`.json` 供程序消费（含完整审计结果与 token 记账），
`.md` 供人阅读（固定 8 段）。

Mock 模式不是"假装成功"：它会去读提示词里的指标 JSON 和片段头，
再按真实结构产出，因此解析、归一化、审计、渲染四条路径都会被真正执行。
如果 Mock 自己编数字，这套护栏在离线场景就等于从未跑过。
