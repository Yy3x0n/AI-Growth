# 数据能力评估（Data Capability Assessment）

> 版本：v1.0　｜　对应阶段：2　｜　证据：`docs/data_quality_report.md` Q-15 ~ Q-24
>
> **这份文档回答一个问题：这套数据到底能支撑哪些分析、不能支撑哪些。**
> 结论先行：它是一份**截面面板（panel）**，不是**生命周期（lifecycle）**数据集。
> 凡涉及"用户从生到死"的分析，在这份数据上都会产出噪音。

---

## 1. 四项实测证据

| # | 现象 | 数值 | 说明 |
|---|---|---|---|
| E-1 | 首次使用日早于注册日的账户 | **490 / 500（98%）** | 中位数早 400 天。`signup_date` 与使用行为无因果关联 |
| E-2 | 首次使用落在数据起始月（2023-01）的账户 | **440 / 500（88%）** | 左截断：数据开始前就"已在使用"，看不出入场时点 |
| E-3 | 24 个月里每月活跃账户数 | **410 ~ 440** | 无增长、无衰退、无季节性，是一条稳态线 |
| E-4 | 每账户已用功能数 | **9 ~ 40（均值 27.6）** | 起点就用了 9 个功能，不存在"从浅到深"的采用路径 |

补充：25,000 条使用记录中，落在该账户**任一**订阅有效期内的只有 22.5%（Q-24）。
说明 `feature_usage.subscription_id` 的挂接与订阅时间线不相关——**使用行为与订阅生命周期是两条独立的随机流**。

## 2. 能力矩阵

| 分析类型 | 能否用真实数据 | 判断依据 | 处置 |
|---|---|---|---|
| 收入结构与规模（MRR / ARPA / 套餐） | ✅ 能 | 订阅表字段完整，月末快照可去重 | 真实数据，见 `core_kpis.csv` |
| 收入集中度（谁贡献大部分收入） | ✅ 能 | 账户级 MRR 可排序 | 真实数据，高价值层占 57.1% 收入 |
| 功能渗透与错误率 | ✅ 能 | 40 个功能、25,000 条记录 | 真实数据，但功能名无语义 |
| 服务负担（工单/响应/CSAT） | ✅ 能（CSAT 分母受限） | 2,000 条工单，满意度缺失 41% | 真实数据，披露 N |
| 流失结构与原因 | ✅ 能 | 600 条事件带原因与退款 | 真实数据，三口径并列 |
| 交叉分层（收入 × 使用 × 服务） | ✅ 能 | 账户级宽表可聚合 | 真实数据，六层互斥 |
| 注册 → 激活漏斗 | ❌ 不能 | E-1 / E-2：锚点失效 | 改用模拟数据，见 §3 |
| 7 日 / 30 日留存 | ❌ 不能 | E-2：队列退化，M+1 恒为 ~83% | 改用模拟数据 |
| 同期群（cohort）留存 | ❌ 不能 | 只有一个巨大队列（2023-01） | 改用模拟数据 |
| 功能采用演化路径 | ❌ 不能 | E-4：起点已用 9 个功能 | 不做；改为截面采用广度分层 |
| 月度增长趋势 | ❌ 不能 | E-3：稳态线，无趋势可讲 | 不做趋势结论，只做结构结论 |
| A/B 实验 | ❌ 不能 | 无分组字段，且样本仅 500 | 模拟实验，见阶段 3 |
| 成本 / Token / 延迟 | ❌ 不能 | 真实表无此字段 | 模拟日志，见阶段 3 |

**能做的 6 项 + 不能做的 7 项，构成本项目的边界。**

## 3. 处置：双层分析架构

```
                    ┌──────────────────────────────────────┐
   T1 真实数据      │  产品结构与健康度                      │
   (RavenStack)     │  收入 · 功能 · 服务 · 流失 · 分层       │
                    │  → 全部可复核，无代理口径              │
                    └──────────────────────────────────────┘
                    ┌──────────────────────────────────────┐
   T2 模拟数据      │  客户生命周期与实验                    │
   (固定种子生成)    │  注册→激活→留存 · A/B · Token 成本     │
                    │  → 全程标注「模拟」，不写入真实结论     │
                    └──────────────────────────────────────┘
```

**为什么不在真实数据上硬做生命周期分析：**

以"注册后 7 日激活率"为例，真实数据能算出 7/500 = 1.4%。这个数字看起来"是个数"，
但它度量的是生成器的随机挂接误差，不是任何业务事实。把它写进报告，等于用一个精确的数字
讲一个错误的故事——这比没有结论更糟。

**为什么模拟数据是可接受的：**

任务书 §2.3 / §2.4 明确允许为 AI 日志与 A/B 实验建立模拟数据，前提是标注清楚。
真实数据缺的是"时间轴"，模拟数据补的正好是这一块，两者职责不重叠、不互相冒充。

---

## 4. 对报告写作的硬约束

1. 出现"注册后"字样的指标，**不得**由真实数据计算。
2. 出现"留存""激活""同期群"的结论，必须注明数据层级（T1 / T2）。
3. 引用流失率必须带口径名（事件口径 70.4% / 净口径 67.8% / 标签口径 22.0%）。
4. 功能分析不得使用「AI 问答」「文档总结」等语义名，真实数据只有 `feature_1..40`。
5. 任何"增长""下降"的趋势描述，先检查 E-3 是否成立（当前：不成立）。

---

## 5. 这套评估本身的价值

对简历项目而言，"发现数据集不支持原定分析并重设方案"比"凑出一份看起来完整的报告"更有说服力：

- 它证明的是**判断力**，不是执行力；
- 面试追问"你怎么知道 1.4% 是假的"时，可以给出 490/500、88%、22.5% 三个可复算的数字；
- 它把"数据清洗"从"补空值去重"升级为"判定数据能回答什么问题"，这是数据运营岗与取数岗的分界线。
